# MCP tool schema size: Zod vs Valibot

This repository measures how large the JSON Schema is that an MCP client receives for the same five tools, when the tool inputs are defined with Zod or with Valibot. It reports characters, bytes and real tokenizer counts, and it shows where the generated schemas differ and why.

It runs on MCP TypeScript SDK v2 (`@modelcontextprotocol/server` and `@modelcontextprotocol/client` 2.4.0), the same SDK as the tutorial repo [flySewa/valibot-mcp-orders](https://github.com/flySewa/valibot-mcp-orders).

The measured results are in [`results/results.md`](results/results.md). That file is generated by the benchmark and should not be edited by hand.

## Headline

Sum of the five tools' `inputSchema`, as received in `tools/list`. A negative percentage means Valibot is smaller. Token counts use `o200k_base` (js-tiktoken).

| Measure | Zod | Zod optimized | Valibot | Valibot vs Zod | Valibot vs Zod optimized |
| --- | ---: | ---: | ---: | ---: | ---: |
| No field descriptions: characters | 4649 | 3363 | 3391 | -27.1% | +0.8% |
| No field descriptions: o200k_base tokens | 1663 | 892 | 901 | -45.8% | +1.0% |
| With field descriptions: characters | 6631 | 5345 | 5373 | -19.0% | +0.5% |
| With field descriptions: o200k_base tokens | 2051 | 1280 | 1277 | -37.7% | -0.2% |

Anthropic `count_tokens` numbers are **not included**: `ANTHROPIC_API_KEY` was not set for this run. See [Reproduce](#reproduce) to add them.

## Reproduce

```bash
git clone https://github.com/flySewa/flySewa-mcp-schema-bench
cd flySewa-mcp-schema-bench
npm ci            # installs the exact versions in package-lock.json
npm run bench     # reruns everything and rewrites results/
```

Optional: set `ANTHROPIC_API_KEY` to add token counts from Anthropic's `count_tokens` API. The model defaults to `claude-opus-5-5` and can be changed with `ANTHROPIC_MODEL`. An invalid key stops the run.

```bash
ANTHROPIC_API_KEY=sk-ant-... npm run bench
```

`npm run bench` deletes and recreates `results/`. Every number in this README comes from that folder.

## Method

### The five tools

Defined once in Zod (`src/schemas/zod.js`) and once in Valibot (`src/schemas/valibot.js`). Names, titles, descriptions and enum values come from one shared file (`src/schemas/meta.js`), so all text is byte-identical across libraries.

| Tool | What it covers |
| --- | --- |
| `register_user` | name, email, age (integer 13 to 120) |
| `schedule_event` | ISO timestamps with offset, ISO date, email array, default value, cross-field rule (end after start) |
| `search_products` | optional nested filters object, enums, number bounds, string array, defaults |
| `update_config` | three levels of nesting, regex, record of booleans, URL, defaults |
| `bulk_update_tickets` | UUID arrays with length limits, enums, arrays of enums, array default |

Each tool is measured in two scenarios: without field descriptions (`bare`) and with a one-sentence description on every field (`described`). Real MCP servers usually describe their fields, and identical description text dilutes any percentage difference, so both are reported.

### Proving the schemas are equivalent

`src/cases.js` holds at least 20 valid and 20 invalid inputs per tool (100 valid, 112 invalid in total). Before anything is measured, `src/equivalence.js` runs every input through both libraries:

- valid inputs must pass in both, and the parsed output (with defaults filled in) must be deep-equal;
- invalid inputs must fail in both;
- any disagreement stops the run with exit code 1.

Where the libraries' built-in validators behave differently, the closest match was used and documented:

| Requirement | Zod | Valibot | Why |
| --- | --- | --- | --- |
| Timestamp with offset | `z.iso.datetime({ offset: true })` | `isoTimestamp()` plus `check(isStrictTimestamp)` | Valibot's `isoTimestamp()` accepts `2026-02-30T…`, a space instead of `T`, and `+0100`. Zod rejects all three. |
| Calendar date | `z.iso.date()` | `isoDate()` plus `check(isStrictDate)` | Valibot's `isoDate()` accepts `2026-02-29` and `2026-04-31`. Zod rejects them. |
| UUID | `z.guid()` | `uuid()` | `z.uuid()` only accepts RFC 9562 version and variant digits. `z.guid()` matches Valibot's `uuid()`. |
| Unbounded integer | `z.int()` | `safeInteger()` | `z.int()` rejects integers above 2^53 - 1. Valibot's `integer()` does not. |
| Email | `z.email()` | `email()` | One known difference left unresolved: Zod accepts `o'neil@example.com`, Valibot rejects it. It is listed in the report and excluded from the pass/fail check. |

`results/<scenario>/divergences.json` and the report show the raw behaviour behind each row.

### How SDK v2 turns a schema into JSON Schema

SDK v2 accepts any [Standard Schema](https://standardschema.dev) that also exposes JSON Schema (`~standard.jsonSchema`). For each tool it calls `schema['~standard'].jsonSchema.input({ target: 'draft-2020-12' })` with no other options, then puts `type: "object"` in front of the result (`standardSchemaToJsonSchema()` in `node_modules/@modelcontextprotocol/server/dist/src-*.mjs`). It validates `tools/call` arguments with `schema['~standard'].validate`.

All three variants are registered with the high-level `McpServer.registerTool()` (`src/mcp.js`):

- **Zod**: the Zod schema itself. Zod 4.6.7 implements `~standard.jsonSchema`.
- **Zod optimized**: a wrapper around the Zod schema's `~standard` object (`zodOptimizedStandard()` in `src/convert.js`). It keeps `vendor`, `version` and `validate` unchanged and replaces `jsonSchema.input` and `jsonSchema.output` with functions that add `libraryOptions: { override: stripFormatPatterns }` before calling Zod's originals. Zod passes `libraryOptions` through to its JSON Schema converter, and `override` runs once for every schema node. `stripFormatPatterns` deletes `pattern` only on a node that also has a string `format`, which is where Zod places its email, date-time, date and UUID regexes. Hand-written `.regex()` patterns have no `format` next to them, so they stay (the `service` pattern in `update_config` is still present in the output).
- **Valibot**: `toStandardJsonSchema(schema)` from `@valibot/to-json-schema`, wrapped the same way to add `libraryOptions: { ignoreActions: ['check', 'partial_check'] }` (`valibotStandard()` in `src/convert.js`). See the known issue below.

Validation is unchanged by both wrappers, because they keep the original `validate` function.

For every variant the benchmark cross-checks the SDK-path output against a direct call (`z.toJSONSchema(schema, { target: 'draft-2020-12', io: 'input' })` and `toJsonSchema(schema, { target: 'draft-2020-12', typeMode: 'input', ignoreActions })`) and stops if they differ. Files: `results/<scenario>/json-schema/<variant>/<tool>.json`. Each library's no-options output is saved under `json-schema/library-defaults/` for reference.

### Known issue: Valibot `toStandardJsonSchema()` and `v.check()` on SDK v2

Our Valibot schemas use `v.check()` (strict dates) and `v.partialCheck()` (end after start). These run custom code and cannot be written as JSON Schema. `toStandardJsonSchema()` takes no options, and the SDK passes none when it calls `jsonSchema.input()`, so the converter's default error mode applies and `tools/list` fails:

```
The "check" action cannot be converted to JSON Schema.
```

The benchmark reproduces this on every run (it registers the unwrapped schemas once and records the error in `results/results.md`).

Workaround used here: keep the schema's `~standard` object and wrap `jsonSchema.input` and `jsonSchema.output` so they pass `libraryOptions: { ignoreActions: ['check', 'partial_check'] }`. `toStandardJsonSchema()` forwards `libraryOptions` to `toJsonSchema()`, so the two custom checks are left out of the JSON Schema and everything else converts as before. The checks still run on the server when a tool is called.

```js
const std = toStandardJsonSchema(schema)['~standard'];
const wrap = (fn) => (options = {}) =>
  fn({ ...options, libraryOptions: { ...options.libraryOptions, ignoreActions: ['check', 'partial_check'] } });
const inputSchema = {
  '~standard': { ...std, jsonSchema: { input: wrap(std.jsonSchema.input), output: wrap(std.jsonSchema.output) } },
};
```

Zod does not hit this: it leaves `.refine()` out of JSON Schema without being asked. Valibot schemas without `check`, `partialCheck` or other custom actions (like the ones in valibot-mcp-orders) work with plain `toStandardJsonSchema()`.

### Real MCP servers

`src/mcp.js` starts one `McpServer` per variant, connects a v2 `Client` over `InMemoryTransport`, calls `tools/list`, and records the exact JSON-RPC message the server put on the transport. Each server is then called once per tool with one valid and one invalid input; the run stops if any server accepts the invalid input or rejects the valid one.

Files: `results/<scenario>/tools-list/<variant>.json`.

### Measuring

For each tool's `inputSchema` taken from the captured `tools/list` response:

- characters: `JSON.stringify(schema).length` (minified);
- bytes: UTF-8 byte length of the same string;
- tokens: `o200k_base` from js-tiktoken, applied to the same string;
- if `ANTHROPIC_API_KEY` is set, two Anthropic counts from `POST /v1/messages/count_tokens`:
  - as text: the minified schema as a user message, minus a request whose message is `{}`;
  - as a tool: the schema as a tool's `input_schema`, minus the same tool with `{"type":"object"}`.

Percentages are `(other - baseline) / baseline × 100`, so a negative number means the other variant is smaller. Totals sum the five tools. The report also gives the token count of all five schemas tokenized together, and the size of the whole `tools/list` response.

`src/diff.js` compares the schemas key by key (ignoring key order), and the report lists each keyword that appears on only one side, with its location and character cost. On this run the only differences are Zod's 7 format `pattern` regexes (about 1,286 characters, absent from Zod optimized and Valibot) and 2 empty `required: []` lists that only Valibot writes (about 28 characters).

Finally, each `inputSchema` is compiled with Ajv's draft 2020-12 build (`ajv/dist/2020.js` with ajv-formats) and run against the same valid and invalid inputs. This shows how much of the real validation a client could learn from the JSON Schema alone.

## Limitations

- **Tokenizer coverage.** `o200k_base` is OpenAI's encoding for the GPT-4o family. Claude, Gemini and open-weight models use different tokenizers, so the o200k numbers are a proxy for them. This run had no `ANTHROPIC_API_KEY`, so it contains o200k_base counts only. The Anthropic code path reached the API and was refused for a dummy key in an earlier test; a full run with a real key has not been done (unverified).
- **Less detail for the model.** Valibot's converter writes `format: "email"` or `format: "date-time"` without a regex. Zod's default output adds the regex it validates with. The Ajv table in the report shows the effect: the Valibot and Zod optimized schemas let through 3 invalid inputs per scenario that Zod's default schema rejects (`a@example.c`, `2026-03-10 14:00:00Z` and `2026-03-10T14:00:00+0100`). Whether a model produces better arguments with the regex present was not tested. All three servers still reject those inputs at call time, because both libraries validate on the server.
- **Wrappers.** Zod optimized and Valibot both rely on a small wrapper around `~standard.jsonSchema` because SDK v2 passes no library options. Without the wrapper, Zod optimized does not exist and the Valibot server fails `tools/list` (known issue above). A reader who copies plain `toStandardJsonSchema()` into a server with custom checks will hit that error.
- **Five tools.** The results depend on how many fields use formats with Zod patterns (email, timestamps, dates, UUIDs). Tools with mostly plain strings, numbers and enums show almost no difference; tools full of emails and timestamps show a large one.
- **Closest-match schemas.** The Valibot schemas need an extra `check()` for timestamps and dates to match Zod's strictness. That check does not appear in JSON Schema, so it does not affect size. A Valibot user who skipped it would get the same JSON Schema but looser validation.
- **Point-in-time versions.** Converter and SDK output can change between releases. Rerun with new versions before quoting the numbers later.
- **Minified JSON.** MCP clients may re-serialise or reformat schemas before giving them to a model. The numbers measure the minified JSON exactly as received.
