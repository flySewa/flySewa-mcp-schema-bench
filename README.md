# MCP tool schema size: Zod vs Valibot

This repository measures how large the JSON Schema is that an MCP client receives for the same five tools, when the tool inputs are defined with Zod or with Valibot. It reports characters, bytes and real tokenizer counts, and it shows where the generated schemas differ and why.

The measured results are in [`results/results.md`](results/results.md). That file is generated by the benchmark and should not be edited by hand.

## Reproduce

```bash
git clone <this repo>
cd mcp-schema-bench
npm ci            # installs the exact versions in package-lock.json
npm run bench     # reruns everything and rewrites results/
```

Optional: set `ANTHROPIC_API_KEY` to add token counts from Anthropic's `count_tokens` API. The model defaults to `claude-opus-5-5` and can be changed with `ANTHROPIC_MODEL`.

```bash
ANTHROPIC_API_KEY=sk-ant-... npm run bench
```

`npm run bench` deletes and recreates `results/`. Every number in this README comes from that folder.

## Method

### The five tools

Defined once in Zod (`src/schemas/zod.js`) and once in Valibot (`src/schemas/valibot.js`). Names, titles, descriptions and enum values come from one shared file (`src/schemas/meta.js`), so all text is byte-identical across libraries.

| Tool | What it covers |
| --- | --- |
| `register_user` | name, email, age (integer 13 to 120) |
| `schedule_event` | ISO timestamps with offset, ISO date, email array, default value, cross-field rule (end after start) |
| `search_products` | optional nested filters object, enums, number bounds, string array, defaults |
| `update_config` | three levels of nesting, regex, record of booleans, URL, defaults |
| `bulk_update_tickets` | UUID arrays with length limits, enums, arrays of enums, array default |

Each tool is measured in two scenarios: without field descriptions (`bare`) and with a one-sentence description on every field (`described`). Real MCP servers usually describe their fields, and identical description text dilutes any percentage difference, so both are reported.

### Proving the schemas are equivalent

`src/cases.js` holds at least 20 valid and 20 invalid inputs per tool (100 valid, 112 invalid in total). Before anything is measured, `src/equivalence.js` runs every input through both libraries:

- valid inputs must pass in both, and the parsed output (with defaults filled in) must be deep-equal;
- invalid inputs must fail in both;
- any disagreement stops the run with exit code 1.

Where the libraries' built-in validators behave differently, the closest match was used and documented:

| Requirement | Zod | Valibot | Why |
| --- | --- | --- | --- |
| Timestamp with offset | `z.iso.datetime({ offset: true })` | `isoTimestamp()` plus `check(isStrictTimestamp)` | Valibot's `isoTimestamp()` accepts `2026-02-30T…`, a space instead of `T`, and `+0100`. Zod rejects all three. |
| Calendar date | `z.iso.date()` | `isoDate()` plus `check(isStrictDate)` | Valibot's `isoDate()` accepts `2026-02-29` and `2026-04-31`. Zod rejects them. |
| UUID | `z.guid()` | `uuid()` | `z.uuid()` only accepts RFC 9562 version and variant digits. `z.guid()` matches Valibot's `uuid()`. |
| Unbounded integer | `z.int()` | `safeInteger()` | `z.int()` rejects integers above 2^53 - 1. Valibot's `integer()` does not. |
| Email | `z.email()` | `email()` | One known difference left unresolved: Zod accepts `o'neil@example.com`, Valibot rejects it. It is listed in the report and excluded from the pass/fail check. |

`results/<scenario>/divergences.json` and the report show the raw behaviour behind each row.

`v.check()` and `v.partialCheck()` run custom code and cannot be expressed in JSON Schema. The Valibot converter is told to skip exactly those two action types (`ignoreActions: ['check', 'partial_check']`). Zod drops `.refine()` from JSON Schema without being told. Neither library's JSON Schema can express "end must be after start".

### Converting to JSON Schema

- **Zod**: `z.toJSONSchema(schema, { target: 'draft-7', io: 'input' })`. These are the same settings the MCP SDK uses internally (`node_modules/@modelcontextprotocol/sdk/dist/esm/server/zod-json-schema-compat.js`).
- **Zod optimized**: the same call with an `override` hook that deletes `pattern` wherever Zod placed it next to a `format` (email, date-time, date, uuid). Hand-written `.regex()` patterns are kept. See `stripFormatPatterns` in `src/convert.js`.
- **Valibot**: `toJsonSchema(schema, { target: 'draft-07', typeMode: 'input', ignoreActions })` from `@valibot/to-json-schema`. The benchmark also calls `toStandardJsonSchema(schema)['~standard'].jsonSchema.input(...)` and stops if the two outputs differ.

Files: `results/<scenario>/json-schema/<variant>/<tool>.json`. Each library's no-options output is saved under `json-schema/library-defaults/` for reference.

### Real MCP servers

`src/mcp.js` starts one MCP server per variant with the official SDK, connects an SDK `Client` over `InMemoryTransport`, calls `tools/list`, and records the exact JSON-RPC message the server put on the transport.

- **Zod**: high-level `McpServer.registerTool()` with the Zod schema. This is the SDK's standard path.
- **Zod optimized** and **Valibot**: low-level `Server` with `ListToolsRequestSchema` and `CallToolRequestSchema` handlers. In SDK 1.32.2, `McpServer` only accepts Zod and offers no hook to change its JSON Schema output, so these two variants need the low-level API.

Each server is then called once per tool with one valid and one invalid input to confirm it validates on the server. The run stops if any server accepts the invalid input or rejects the valid one.

Files: `results/<scenario>/tools-list/<variant>.json`.

### Measuring

For each tool's `inputSchema` taken from the captured `tools/list` response:

- characters: `JSON.stringify(schema).length` (minified);
- bytes: UTF-8 byte length of the same string;
- tokens: `o200k_base` from js-tiktoken, applied to the same string;
- if `ANTHROPIC_API_KEY` is set, two Anthropic counts from `POST /v1/messages/count_tokens`:
  - as text: the minified schema as a user message, minus a request whose message is `{}`;
  - as a tool: the schema as a tool's `input_schema`, minus the same tool with `{"type":"object"}`.

Percentages are `(other - baseline) / baseline × 100`, so a negative number means the other variant is smaller. Totals sum the five tools. The report also gives the token count of all five schemas tokenized together, and the size of the whole `tools/list` response.

`src/diff.js` compares the schemas key by key (ignoring key order) and the report lists each keyword that appears on only one side, with its location and character cost.

Finally, each `inputSchema` is compiled with Ajv and run against the same valid and invalid inputs. This shows how much of the real validation a client could learn from the JSON Schema alone.

## Limitations

- **Tokenizer coverage.** `o200k_base` is OpenAI's encoding for the GPT-4o family. Claude, Gemini and open-weight models use different tokenizers, so the o200k numbers are a proxy for them. The Anthropic numbers are only produced when `ANTHROPIC_API_KEY` is set, and the published run did not have a key, so the published results contain o200k_base counts only. The Anthropic code path was not exercised in that run (unverified).
- **Less detail for the model.** Valibot's converter writes `format: "email"` or `format: "date-time"` without a regex. Zod's default output adds the regex it validates with. Ajv results in the report show the effect: the Valibot and Zod optimized schemas let through 3 invalid inputs per scenario that Zod's default schema rejects (`a@example.c`, `2026-03-10 14:00:00Z` and `2026-03-10T14:00:00+0100`). Whether a model produces better arguments with the regex present was not tested. All three servers still reject those inputs at call time, because both libraries validate on the server.
- **Server path asymmetry.** The default Zod server uses `McpServer`, which adds `"execution":{"taskSupport":"forbidden"}` to each tool. The other two use the low-level `Server`, which does not. This affects the full-response numbers only, and the report says so. The per-schema numbers compare `inputSchema` objects alone.
- **Five tools.** The results depend on how many fields use formats with Zod patterns (email, timestamps, dates, UUIDs). Tools with mostly plain strings, numbers and enums show almost no difference; tools full of emails and timestamps show a large one.
- **Closest-match schemas.** The Valibot schemas need an extra `check()` for timestamps and dates to match Zod's strictness. That check does not appear in JSON Schema, so it does not affect size. A Valibot user who skipped it would get the same JSON Schema but looser validation.
- **Point-in-time versions.** Converter output can change between releases. Rerun with new versions before quoting the numbers later.
- **Minified JSON.** MCP clients may re-serialise or reformat schemas before giving them to a model. The numbers measure the minified JSON exactly as received.

## Project layout

```
src/
  bench.js          entry point for npm run bench
  schemas/          tool definitions (shared metadata, Zod, Valibot, date helpers)
  cases.js          equivalence inputs and known divergences
  equivalence.js    stop-on-disagreement check
  divergences.js    raw comparison of built-in validators
  convert.js        JSON Schema conversion per variant
  mcp.js            MCP servers, in-memory client, tools/list capture
  tokens.js         o200k_base and Anthropic token counting
  diff.js           key-by-key schema diff
  report.js         writes results/results.md
results/            generated output (committed so readers can inspect it)
```
